# プルリクエストを出す

前提を確かめる → pint → テスト → 受け入れ条件 → 設計書 → コミットと PR 作成 → 報告、の順に進める。途中で問題が出たら、PR を出さずに止まって報告する。

## 1. 前提を確かめる

```bash
git status -s
git branch --show-current
git diff HEAD --stat
```

- `main` の上にいたら、機能ごとのブランチを切る決まりなので、進めずに聞く
- 対応するイシュー番号を、ブランチ名（`feat/3-fortify-setup` なら 3）か会話から確かめ、`gh issue view <番号>` で完了条件を読む。ブランチ名や会話から番号がわからなければ聞く。`chore` の作業のように対応するイシューが無いとわかっていれば、聞かずに進める
- 差分に、この作業と関係ないファイルや `.env` が混ざっていないか見る。混ざっていたら、コミットに入れるかを聞く

## 2. pint を実行する

```bash
vendor/bin/pint --dirty
```

PHP の変更が無ければ省く。`--dirty` を付けるのは、未コミットのファイルだけを整形するため。付けないと、触っていないファイルまで整形されて、差分が関係ない変更で埋まる。

整形されたファイルは差分に含まれるので、そのままコミットに入れる。

## 3. テストを回す

```bash
./vendor/bin/sail test
```

`mysql` コンテナが要る。起動していなければ、起動はユーザーの役割なので、`./vendor/bin/sail up -d` をお願いして止まる。

失敗したら PR は出さず、結果を報告する。通るまで直してよいかは、原因によってユーザーに確かめる。deprecated は失敗ではないが、PR 本文に内容を書く。

## 4. 受け入れ条件を判定する

`docs/acceptance-criteria.md` から、この PR で対象にする行を選ぶ。イシューの「受け入れ条件」と `docs/features.md`「実装の順序」が手がかりになる。

画面で確かめる行がある PR は、先に `verify` skill で確かめておく。済んでいれば、その判定（`uat-shots/README.md`）を本文に載せる。済んでいなければ、ここで `verify` を使うか、ユーザーに聞く。`uat-shots/` はコミットに入れない（手順 1 の「関係ないファイル」にも当たる）。

- テストや実際の操作で確かめられた行は、合否を書く。確かめていないのに合格にしない
- 自分で確かめられない行は、手順を添えてユーザーに判定をお願いし、返事を待つ
- 後の段階の画面が前提の行は、「段階 <番号> で判定」と書く
- 判定する行が無ければ、そのことを書く

## 5. 設計書を確かめる

実装を変えたら、同じ作業の中で該当する設計書も直す決まりなので、差分と設計書が食い違っていないか見る。食い違っていれば、設計書を先に直す（`docs/requirements.md` は直さず、`docs/questions.md` に確認事項として挙げる）。回答が想定と違った Q-xx があれば、参照している設計書とテストも直す。

## 6. コミットして PR を作る

ファイルを名前で指定してステージする。`git add -A` は、関係ないファイルが混ざりやすいので使わない。

コミットメッセージは日本語で、`feat: 書籍一覧表示を実装` の形にする。接頭辞は変更の種類に合わせる。

```bash
git commit
git push -u origin <ブランチ名>
gh pr create --base main --title "<コミットと同じ形>" --body-file <本文のファイル>
```

本文のファイルはスクラッチパッドに置く。本文は次の形にする。

```markdown
## 概要
<1〜2 文で目的>（`docs/features.md` 段階 <番号>）

## 変更内容
- <変更を 1 行ずつ>

## テストの実行結果
`./vendor/bin/sail test`

<結果の行。deprecated があれば内容も>

## 受け入れ条件
- AC-x-x：合格 / 不合格 / 段階 <番号> で判定

Closes #<イシュー番号>
```

- 受け入れ条件は、その PR で対象にした行をすべて載せる
- 対応するイシューが無ければ、`Closes` の行を省き、概要にイシューが無いことを書く
- レビューで見てほしい点や、この PR の時点で動かないものがあれば、節を足して書く
- コミットと PR の署名の指定が会話にあれば、それに従う。`Closes` の後ろに置く

## 7. 報告する

PR の URL と、テスト・受け入れ条件の結果を伝えて、止まる。マージはユーザーの役割なので行わない。
