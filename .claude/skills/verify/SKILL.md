# 完了条件と受け入れ条件を確かめる

条件を取り出す → 前提を確かめる → 1 行ずつ確かめて証拠を残す → 判定する → uat-shots/README.md にまとめる → 後片付けをして報告する、の順に進める。確かめていない行を「満たす」にしない。

## 1. 条件を取り出す

```bash
gh issue view <番号>
```

イシューの「完了条件」と「受け入れ条件」を、1 行ずつ取り出す。完了条件には C1、C2…、受け入れ条件にはイシューの ID（AC-1-1 など）を付ける。

- 番号が無ければ、ブランチ名（`feat/17-auth` なら 17）か会話から確かめる。わからなければ聞く
- 受け入れ条件の文面は、`docs/acceptance-criteria.md` と食い違っていないか見る。食い違っていたら、勝手に直さず、報告する
- イシューに入っていない行（後の段階で判定する行）は、確かめない

## 2. 前提を確かめる

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://localhost/login
ls public/hot
```

- アプリが答えない、または `public/hot` が無い（Vite の開発サーバーが動いていない）ときは、止まって、`./vendor/bin/sail up -d` や `sail npm run dev` をお願いする。起動はユーザーの役割
- 開発用の DB の中身を、先に見る（ユーザーの数とメールアドレスなど）。`migrate:fresh --seed` は、ユーザーが手で入れたデータも消えるので、勝手に実行しない。シーダーのデータが残っていれば、そのまま使う
- 会員登録のように DB に行が増える操作は、増えることを先に伝える。終わったら、増えた分（メールアドレスなど）を報告する
- 回数制限などで、実在のユーザーを止めないよう、存在しないメールアドレスを使う

## 3. 1 行ずつ確かめる

画面の操作は Playwright MCP で `http://localhost` を開いて行う。ツールは `ToolSearch` で `select:mcp__playwright__browser_navigate,...` の形で読み込む。

- ブラウザには、前のログインが残っていることがある。まずログアウトして、未ログインから始める
- 実際のクリックが、ページに届かないことがある（メニューの開閉、フォーム送信など。クリックのイベントが 1 件も記録されない）。そのときは、ページ内の JavaScript からクリックや `requestSubmit()` を送ってよい。ただし、どの行をその方法で確かめたかを、必ず報告に書く。人の手での操作と完全に同じではない
- 画面で確かめられない完了条件（テストなど）は、実行結果をテキストで残す。例：`./vendor/bin/sail test` の結果の行を `uat-shots/` に保存する。deprecated は失敗ではないが、内容を書く
- 回数制限のように、画面で何度も送る条件も、実際に 6 回送るなどして、画面で確かめる。`curl` は補助にとどめる
- 入力エラーのような「種類が多い条件」は、種類をすべて数え上げて、全部確かめる。一部だけ見て「全項目を確かめた」と書かない。確かめていない範囲（境界値の「通る側」など）は、書く

## 4. 証拠を残す

スクリーンショットは、作業ディレクトリの `uat-shots/` に置く。`browser_take_screenshot` の `filename` に `uat-shots/<名前>.png` を指定する。Playwright は、作業ディレクトリの外には保存できない。

名前は、どの行のものか分かる形にする。

- 受け入れ条件：`AC-1-1_register-form.png`。1 行に複数枚なら `AC-14-1_1_menu-open.png`、`AC-14-1_2_after-logout.png`
- 完了条件：`C4_register-while-logged-in.png`。1 行に複数の確認があれば `C3-a_...png`、`C3-b_...png`

撮ったら、必ず `Read` で画像を開いて、期待した画面かを自分の目で確かめてから判定する。画像を見ずに合格にしない。

ページの画像には URL が写らない。移動が絡む行は、ブラウザ操作の結果に出る URL（開いた URL と、着いた URL）を控えて、README に書く。

## 5. 判定する

行ごとに、次のどれかを付ける。

- **満たす**：条件の文面どおりになっていることを、画面か実行結果で確かめた
- **満たさない**：食い違った。何がどう違うかを書く
- **確かめられない**：環境や前提が足りない。何が足りないかを書く

理由は、「何をして、何が見えたか」を書く。「問題なし」だけにしない。

満たさない行があれば、直すかをユーザーに聞く（実装を直すのは、頼まれてから）。直したら、その行だけでなく、影響する行も確かめ直す。

## 6. uat-shots/README.md にまとめる

条件ごとに、次を書く。条件の文面は、イシューの文面そのままにする。同じ画像を複数の条件で使うときは、どの条件でも画像とファイル名を載せる。

```markdown
### AC-1-1　<条件の文面>
- 判定：満たす
- 理由：<何をして、何が見えたか>
- URL：<開いた URL> を開く → <着いた URL>　／　操作：URL 直接 / 実クリック / JS

![AC-1-1](AC-1-1_register-form.png)
`AC-1-1_register-form.png`
```

先頭に、読み方（操作の略称の意味、確認日、使ったユーザー）を書く。

## 7. 後片付けをして報告する

- ブラウザを閉じてから、`.playwright-mcp/`（スナップショットとログ）を消す。ブラウザを使うたびに作られるので、最後に消す
- `uat-shots/` は、ユーザーが人の手で確かめるための証拠なので、自分では消さない。コミットにも含めない（git に追跡されていないまま残す）。報告に「確認が終わったら、消してと言ってください」と添える
- ユーザーが「確認した」「消して」と言ったら、`uat-shots/` を消す。消す前に、`ls uat-shots` と `git ls-files uat-shots`（追跡されているファイルが無いこと）を見る。消したら `git status -s` で、残りが無いことを確かめる
- 増えた DB の行を報告する。消すかはユーザーが決める

報告は、行ごとの表（条件・判定・理由・証拠）にする。次も必ず書く。

- 確かめていない範囲と、その理由
- 実際のクリックでなく、JavaScript で確かめた行
- 画面の見た目の最終確認は、人の手で行う前提であること（`docs/acceptance-criteria.md` は、人が手で試すためのもの）
