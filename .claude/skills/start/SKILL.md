# イシューに着手する

イシューを確認する → main を最新にする → ブランチを切る → 設計書を読む → 計画の承認をもらう、の順に進める。承認をもらうまで実装しない。

## 1. イシューを確認する

番号の指定があれば内容を読む。

```bash
gh issue view <番号>
```

番号の指定が無ければ、一覧を見せてどれにするか聞く。

```bash
gh issue list
```

次のときは、進めずにユーザーに聞く。

- イシューが閉じている
- 同じ番号のブランチがすでにある（`git branch -a --list "*/<番号>-*"` で確かめる）。作業の続きかもしれないので、新しく切らない

## 2. main を最新にする

```bash
git status -s
git checkout main
git pull origin main
```

未コミットの変更があれば、`git checkout` の前に止まって、変更の内容を伝えて聞く。別の作業の途中かもしれず、切り替えると新しいブランチに混ざるため。

pull が失敗したら、そのまま進めずに結果を伝える。古い main から切ると、後でコンフリクトの元になるため。

## 3. ブランチを切る

```bash
git checkout -b <接頭辞>/<番号>-<内容>
```

例：`feat/3-fortify-setup`

- 接頭辞はイシューの種類で決める。新しい機能や段階の実装は `feat`、不具合の修正は `fix`、設計書だけの変更は `docs`、それ以外の雑務は `chore`。迷ったら `feat`
- 内容は、イシューのタイトルから取った短い英語（小文字とハイフン、2〜3 語）

## 4. 設計書を読む

イシューに対応する設計書を読む。設計書が正なので、記憶や推測で進めない。

- `docs/features.md`：該当する機能（F-xx）。段階のイシューなら「実装の順序」の行と、表の下の補足
- `CLAUDE.md`「決めごとの在りか」の表で、その作業に関係する設計書
- `docs/questions.md`：関係する Q-xx。状態欄が空のものは未確定
- `docs/acceptance-criteria.md`：その作業で判定する行

## 5. 計画の承認をもらう

イシューの大きさで分ける。迷ったら計画を立てるほうにする。後から手戻りするより、一度確認するほうが安いため。

### 計画を出すほどでもない小さい件

変更が 1〜2 ファイルに収まり、設計の判断が無く、やることを数行で言い切れるもの（例：設計書の文言の修正、設定値を 1 つ変える）。

plan モードには入らず、何をするかだけを伝えて、承認の返事を待つ。

### それ以外

`EnterPlanMode` で plan モードに入り、計画を立てて、`ExitPlanMode` で承認をもらう。計画には次を入れる。

- 変更するファイルと、変更の内容
- 追加するテストと、回し方
- 同じ作業の中で直す設計書
- 設計書に無くて判断が要る点、設計書と実装が食い違っている点
- ユーザーが自分で行う作業（コンテナの起動、Fortify の導入のようなコマンドの実行など）

### どちらでも伝えること

- 切ったブランチ名と、まだローカルだけで push していないこと
- コンテナが要る作業なら、`./vendor/bin/sail up -d` で起動してほしいこと（コンテナの起動はユーザーの役割）

承認をもらったら実装に入る。コミット、push、PR の作成は、頼まれるまで行わない。
