# 段階のイシューを立てる

調べる → 質問する → 案を見せる → 承認後に作る、の順に進める。

## 1. 調べる

次を読み、その段階で作るものと前提を確かめる。設計書が正なので、記憶や推測で書かない。

- `docs/features.md`「実装の順序」：その段階の行と、表の下の補足
- `docs/questions.md`：その段階に関係する Q-xx。状態欄が空のものは未確定
- `docs/acceptance-criteria.md`：その段階で判定できる行。前提の画面・ルート・シーダーが、その段階までに揃うかで判断する
- 必要な範囲の、該当する設計書（`CLAUDE.md`「決めごとの在りか」）
- 現在のコードの状態と `gh issue list --state all`：すでに済んでいる作業や、同じ段階のイシューが無いか

## 2. 決めることを先に質問する

答えによってイシューの内容が変わることだけを `AskUserQuestion` で聞く。設計書で決まっていることや、普通の決め方で足りることは聞かない。

聞くことの例：

- 判定できる受け入れ条件の行が無い、または頼まれた内容と合わないときの扱い
- ユーザーが自分で行う作業と、Claude が行う作業の境目
- 隣の段階との境目が設計書から読み取れないとき
- 設計書で文言や値が未確定のもの

聞くことが無ければ、質問は省いて案に進む。

## 3. 案を見せる

作る前に、本文の案を会話に出す。質問に答えをもらっていても、案の承認とは別なので、ここで止まって返事を待つ。イシューの作成はユーザーが確認してから行う。

本文は短くする。次の形を使い、これ以外の節を足さない。

```markdown
## 概要
<1〜2 文で目的>。（`docs/features.md` 段階 <番号>）

## 実装する内容
- <作るものを 1 行ずつ>

## 完了条件
- [ ] <できあがった状態を、確かめられる形で 1 行ずつ>
- [ ] `./vendor/bin/sail test` が通る

## 受け入れ条件
- [ ] AC-x-x：<`docs/acceptance-criteria.md` の文面>
```

判定する行が無い段階では、「受け入れ条件」の節の中身を「`docs/acceptance-criteria.md` に段階 <番号> で判定する行は無い」の 1 行にする。

書き方：

- 「実装する内容」は 3〜6 行を目安にする。設定値の細部、ファイルごとの手順、Q-xx の一覧は書かない
- 完了条件は作業手順ではなく、結果の状態を書く
- 受け入れ条件は、その段階で判定する行をすべて、ID と文面を設計書のまま 1 行ずつチェックボックスで書く。後の段階で判定する行は入れない
- 範囲外、担当、PR の書き方の節は作らない

本文から外した内容（担当、細かい作業、範囲外、後の段階で判定する行）は、案の下に箇条書きで添えて、イシューに書かなくても作業では守ると伝える。

## 4. 承認後に作る

```bash
gh issue create --title "段階<番号>: <内容>" --label enhancement --body-file <本文のファイル>
```

- 本文のファイルはスクラッチパッドに置く
- 直しを頼まれたら、改めて案を見せ、承認後に `gh issue edit <番号> --body-file <本文のファイル>` で更新する
- 作ったらイシューの URL を伝える。ユーザーの作業が先に必要なら、それも伝える
- 実装は、頼まれるまで始めない
