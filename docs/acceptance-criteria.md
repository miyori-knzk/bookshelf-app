# 受け入れ条件

人が手で全部試して、1 行ずつ合否を付けるためのもの。基本機能の行に、★応用機能（段階 9 以降）の行を足している。どの行も、確かめる工程を 2〜4 行で説明できる大きさにしている。
網羅は `docs/test-viewpoints.md` に置く。

## 試す前の準備

- 単位を始める前に、`sail artisan migrate:fresh --seed` で DB を入れ直す。この表の書籍名・ジャンル名・ユーザーは、シーダーのデータ（要件「シーディング」）。
- ログインは、シーダーのユーザー（パスワードはどれも `password`）で行う。書籍の作成者は、どれも山田太郎（`yamada@example.com`）。
- 同じ単位の中は、上から順に試す。前の行で作ったデータを使う行がある。
- 画面を試す間は、`sail npm run dev` を動かしておく（CSS と JS の読み込みに必要）。
- ブラウザで試す。公開API（AC-15）の登録・更新・削除はブラウザだけでは送れないため、Postman などで送る。

「前提」の列は、その行が前提にしている確認事項（`docs/questions.md`）。回答が想定と違ったら、その行を直す。

### ページ送りの準備（AC-3-17 の前に 1 回だけ実行する）

「ページ確認01」〜「ページ確認12」を登録し、01〜11 だけにジャンル「小説」を付ける。

```bash
./vendor/bin/sail artisan tinker --execute='App\Models\Book::factory()->count(12)->sequence(fn ($sequence) => ["title" => sprintf("ページ確認%02d", $sequence->index + 1)])->create(["user_id" => 1])->take(11)->each(fn ($book) => $book->genres()->attach(1));'
```

12 冊目にジャンルを付けないのは、ジャンルの条件が引き継がれないと件数が 12 件になり、気づけるようにするため。

### 並び順の仕様（AC-3-12〜3-15 の根拠）

| 値 | 並び順 |
| --- | --- |
| latest（デフォルト） | 登録日が新しい順 |
| oldest | 登録日が古い順 |
| title | タイトル昇順 |
| rating | 評価が高い順（レビューがない書籍は最後に表示） |

- ※提供ビューの「新しい順」の値は `latest` ではなく `newest`。段階 10 で扱いを決める。
- ※評価が同じ書籍どうしの順番は仕様に無い。段階 10 で決める（AC-3-15 は、この順番によらず判定できる）。

```json
{
  "title": "認証の確認",

```

### 仕様（AC-15-10〜15-19 の根拠）

- 書き込み系（`POST`・`PUT`・`DELETE /api/v1/books`）に、Sanctum のトークン認証を入れる。
- 認証済みの利用者のうち、書籍の所有者だけが更新・削除できる。
- 未認証のときと認可エラーのときは、適切な HTTP ステータス（401・403）を返す。

段階 15 では、既存の AC-15-5〜15-9 も直す（どれもトークンを付ける。`user_id` は送らず、登録者はトークンの持ち主になる）。

### レポートの仕様（AC-18 の根拠）

認証時は次の 4 種類の統計を表示し、未認証時は `/login` へ移動する。

1. 基本サマリー：総レビュー数、読了冊数（ユニーク書籍数）、平均評価点
2. 評価分布：1〜5 星ごとの件数を横バーで表示
3. 高評価書籍 TOP5：4 星以上の書籍を、評価の高い順に最大 5 件表示（書籍詳細リンク付き）
4. ジャンル別評価傾向 TOP5：ジャンルごとの平均評価と件数を、高い順に最大 5 件表示（ジャンル詳細リンク付き）

※段階 14 で決める点

- 読了冊数の元データ。「レビューした書籍の数」なら AC-18-3 は 7、AC-18-9 は 8。「読了にした読書計画の書籍の数」なら、どちらも 0（読了させて確かめる行を足す）。
- 評価（平均評価）が同じ書籍・ジャンルの順番。AC-18-5・18-6・18-10 は、この順番によらず判定できる。
- 同じ書籍に 4 星以上のレビューを複数投稿したとき、高評価書籍に 1 回だけ出すか。

### 仕様（16・17・19 節で、段階 12・13 で決める点）

- 状態の種類と名前。日次バッチは、期日を過ぎた計画の状態を自動で変える。
- 期日の入力チェック（過去の日付）、同じ書籍の計画の重複、エラーと成功のメッセージ。
- 読了した計画の編集・読了を、サーバー側でも拒否するか。期限切れの計画の期日を未来に変えたときの状態。
- 通知を発火する条件と文面。上の行は、提供ビューの 3 種類（3 日前・当日・3 日後）を想定している。
- バッチを実行する時刻と、Sail でのスケジューラーの動かし方。
